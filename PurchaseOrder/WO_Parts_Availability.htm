About this report

How availability, sequencing and procurement are computed

Availability engine

Each work order's raw components are matched against, in order: stock committed to that WO on a pick, shared available-to-pick stock in its location group, purchase orders raised for the WO's manufacture order (express POs), blanket purchase orders, and finished-good output scheduled from other work orders. Stock is allocated FIFO in scheduled-start order, so an earlier WO gets first claim on shared stock.

  • Buildable now — every component is available today.
  • Waiting — fully sourced, but the binding component arrives on a future PO/WO date (the Ready date). A padlock marks a date secured by an MO-linked PO.
  • Contested — stock physically exists, but earlier-scheduled WOs have first claim; resequencing (not purchasing) would secure it.
  • Unmet — a genuine shortage that needs a PO or MO.

Planner

A two-pane what-if scheduler. The left pane is the current schedule; click Plan on a work order to move it to its earliest material-ready date. Planned changes stage on the right, where the scenario re-runs the availability engine and cascades staged dependencies (a consumer never starts before its producer finishes). Plan all recommended stages every buildable WO at once; Revert removes a staged change. When you're happy, Apply writes the new start/finish dates for every planned work order to Fishbowl. This is material-only — it does not model machine capacity or labour.

Business calendar & scheduling maths

When the Planner proposes a new start and finish for a work order, it uses the business calendar set in Settings (business days plus opening hours, saved org-wide by an administrator). It works in whole days, like a wall calendar — it decides which days the build runs on, not the clock time.

  • Start day — the work order moves to the earliest day its materials are ready (never in the past). If that day isn't a working day, it rolls forward to the next one.
  • How long it takes — the build time comes from the BOM's estimated time × the quantity being built. That total is spread across working days, giving each day one full "opening hours" worth of capacity (for example, 8:00–17:00 = 9 hours a day). Weekends and any non-working days are simply skipped.
  • Finish day — in plain terms: total build hours ÷ hours per working day, rounded up, tells you how many working days the build needs. The finish lands that many working days out from the start (a job that fits in one day finishes the same day; anything longer carries onto the following working day, jumping over weekends and days off).
  • Knock-on effects — if one work order feeds another, the consumer is pushed to start no earlier than the day after its producer finishes (again snapped to a working day), and its own length is worked out the same way.

Worth knowing: this is deliberately simple. It assumes each build gets a whole working day at a time, doesn't split a part-day, and doesn't limit how many work orders share the same day (no machine or labour capacity). It also assumes the BOM's estimated time is per unit. And when you Apply, only the dates change — each work order keeps its existing time of day. Work orders without an estimated build time keep their original calendar length.

Procurement

The genuine shortages across the work orders in view, split into To Purchase (grouped by default vendor) and To Manufacture (parts with a BOM). Create PO / Create MO write directly to Fishbowl via the REST API; supply is created in the same location group the shortage sits in so the engine can match it. Creating a PO does not email the vendor.
