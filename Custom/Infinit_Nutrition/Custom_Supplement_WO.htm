📖 How to read this report

The note format

Each custom-supplement line carries its customisation in soitem.note as Attribute: Level pairs, separated by commas, semicolons or newlines:

Flavour: Banana, Electrolyte Mix: Med Caffeine: 50mg

Exactly three things are customisable — everything else on the BOM is a fixed base ingredient and must not appear in the note:

  • Flavour — which flavour raw good fills the flavour slot
  • Electrolyte Mix — Low / Med / High (400 / 500 / 1000 mg per serve, which are also accepted as the level)
  • Caffeine — 0 / 25 / 50 / 75 / 100 mg per serve

Matching ignores case, spaces and punctuation, so electrolyte: low and Electrolyte Mix: Low are the same, and caffeine takes 50, 50mg or 50 mg (and None for zero). A fragment with no colon is treated as prose and ignored, so an ordinary shipping comment can sit alongside the attributes.

An attribute we can't map — an unknown name, or a caffeine/electrolyte value off its scale — renders as an ⚠ amber chip and blocks the build. It is never silently dropped: catching bad notes is the point of this report.

Flavour is the exception. Its list is open, so any flavour is accepted; one with no part mapped yet shows as a ✎ dashed chip, keeps the BOM's own flavour line, and warns instead of blocking — swap the raw good by hand on the work order.

How the recipe resolves

The variable quantities live in this report's recipe configuration, deliberately separate from the Fishbowl BOM, so an admin can adjust them without editing the BOM. Per component:

  • a base ingredient keeps the BOM's own quantity
  • a variable item takes an absolute figure per pack from the configuration, which replaces whatever the BOM line says
  • Flavour also says which FLV-RTU-* raw good fills the slot — the mass is the same whichever flavour
  • then every line is multiplied by the ordered quantity

For the 25-serve pack the configured figures are electrolytes 49.07 / 61.14 / 122.28 g for Low / Med / High, and caffeine 0 / 1.3 / 2.5 / 3.8 / 5 g for 0–100 mg per serve.

The Recipe button in the topbar opens the configuration, where an admin chooses each pack's base BOM and edits its items, levels and quantities. Anyone can read it; only an admin can publish a change. Adding a pack there is all it takes to support a new size — no BOM edit, no report change.

Those grams are not the pure ingredient mass, which is why they are stored verbatim rather than calculated: 100 mg of caffeine per serve on a 25-serve pack is 5 g of raw material, not 2.5 g, because the raw good is roughly half caffeine by weight. Deriving the figure would understate it by half.

A pack with no configuration, a level with no figure, or a flavour whose part is not in Fishbowl all keep the BOM quantity, show the adjustment struck through, and warn naming what to set — nothing is ever guessed.

Quantities stay in each BOM line's own UOM — bomitem.uomId often differs from part.uomId, and the API takes an explicit UOM per item, so the BOM's own figures are never converted. A substituted flavour has no BOM line of its own, so it uses its part's base UOM.

What blocks a build

Create stays disabled until all of these hold:

  • the note parsed with no unknown attributes and no off-scale values
  • an active BOM exists whose finished good is this product's part
  • every component resolved to a live part and UOM
  • at least one component with a quantity above zero
  • the sales order has a location group

Deliberately not blockers: a staged sub-assembly, a variable-quantity line, an optional raw good, an unmapped flavour, or a pack with no serves mapping. Each warns and leaves the BOM figure alone, because this report produces the ingredient list a person reviews before creating — not a contract that has to map perfectly.

Fixture rows can't post. Rows badged sample, and recipes that fell back to the built-in fixtures, are refused outright.

What gets created

One POST /api/manufacture-orders carrying the full overridden configurations[].items[] — the finished good plus every component. Fishbowl generates the work orders when the MO is Issued. Nothing is ever patched afterwards: updating an issued MO regenerates its work orders.
