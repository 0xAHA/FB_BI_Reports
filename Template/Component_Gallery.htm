📖 How this gallery works

What it is

Every shared style (fb-styles §1–37) and widget (fb-lib, fb-doc, fb-label), working, with its code. Start a report from a template in Template/; come here for the piece you need.

The marks

Current use it in a new report.
Dashboards only the v1.2 dashboard chrome: not in a report.
Legacy found in older pages: don't start new work with it.

Copying

Each code box is the section's real markup and the source of the function that runs it. Copy puts it on the clipboard. The header selector hides the sections you don't need.

Every shared style and widget, live. The page itself is a report: its header, Filters panel, Settings and Help drawers, toasts and debug console are the real thing. Each section says what a component is for, whether to use it in a new report, and has the code to copy. Guides: docs/building-apps.md (which piece does what), docs/fb-doc.md (printing). Shared code is in scripts/: never copy a shared function into a page. The code boxes call a few page helpers (esc, sqlStr, debugLog, money, q): they are in the Queries section, as the templates have them. Toasts, the confirm, tooltips and the filter-strip drop-downs are fb-lib's (FBLib.Common.toast / confirmModal / tooltips / fdrop): no page copies them.

Confirm before a write

FBLib.Common.confirmModal · fb-styles §12

Use it for the one question before a write or a delete. It lists exactly what will change (and the request, for a write) and resolves true on OK, false on Cancel, the ×, Esc or the backdrop. danger: true makes OK red (.ds-btn-danger) and starts on Cancel; wide: true fits a table; note sits beside the buttons. 8 · Saved views

FBLib.FilterViews: My views and Company views behind one button.

Saved views

FBLib.FilterViews.attach (custom mode)

Use it for letting users save and reopen a set of filters: the bookmark button opens My views (per user) and Company views (published by an admin, read live by everyone); ☆ makes one open by default; the dot on the button means the screen no longer matches the view. Change the form, then Save as new…; load the sample view; change a filter and see the dot. Don't build a page-local views list or drawer.

How a real report wires it. Pass capture (the filters as JSON) and restore (put them back and reload; may return a Promise); matches or canon decide "modified"; describe is the one-line summary. Call views.changed() after every filter change. Before the first query, views.adoptDefault() returns the starred view's state (or null) to start from; or call openDefault() once the page is ready. Leave out storage: My views then live in the page's FBLib.Settings (views.<TILE>), Company views in FBLib.SharedData at FB_REPORT.key + '.shared.v1'; editors: true lets the report's Edit Settings users publish too. This demo keeps My views in memory and turns Company views off (company: false), so nothing is saved.

Queries: the q() helper and the load token

runQueryAsync · FBLib.Common.debugLog · the page helpers the other code boxes use

Use it for every read. One helper sends the SELECT through runQueryAsync, logs it and its timing to the debug console and throws with the query's name on failure; each load takes a token so an older answer that arrives late is dropped instead of painting over a newer one. SQL starts with SELECT, uses lower-case tables, escapes values inline (sqlStr) and casts bit(1) columns (activeflag+0). The helpers below (esc, sqlStr, debugLog, money, ymd) are the ones the other code boxes call. Don't use runQuery for anything slow, build SQL from unescaped input or SELECT a bare NULL. The button runs two overlapping loads; the slower, older one is dropped.
