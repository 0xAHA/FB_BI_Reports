Using the Fishbowl API Tool

How to drive this window. For the API itself — what the endpoints do and how to build an integration on them — switch to Fishbowl API guide above.

The official documentation

This guide is about driving the window. For the API itself, three sources are authoritative, and all three open in your browser rather than in this tab:

  • Fishbowl help centre — REST API — the published article. Start here for what the API is and how authentication works.
  • http://<your server>:2456/apidocs — the browsable reference your server generates for itself, listing exactly the endpoints that server has. Reachable from the Official docs button above, which fills in the address of whichever server you are pointed at.
  • http://<your server>:2456/apidocs.json — the same reference as machine-readable JSON, and unauthenticated, so it works before you sign in. This is what the tool's endpoint catalog is built from; see Keeping the endpoint list current.
The server is the authority. The endpoint list in this tool is a catalog that ships with it, and a given Fishbowl build may have endpoints it does not, or lack ones it has. When they disagree, /apidocs.json is right — and Settings ▸ Endpoint catalog ▸ Check for updates will show you exactly where the two differ.

Connecting

There are two ways in, for two different jobs.

Sign in

The normal path. The first sign-in with a given app name and id registers the app, and an administrator has to approve it in Fishbowl under Settings ▸ Integrated Apps before it will work. Change the name or id under Integrated app identity only to reuse an approval that already exists.

MFA arrives as a header, not a message. If the account has MFA enabled, the server answers 401 with an MFA: Required header. Enter the code and sign in again — a bad password looks the same otherwise.

Paste a token

Not a shortcut. This is how you reproduce a failing call with the same session an integration used, which is usually the only way to tell an access-right problem apart from a payload problem.

A pasted token is tested before it is accepted, is never written to disk, and disconnecting drops it without logging that session out — the session belongs to whoever issued it.

Remembering a password

Tick Remember this password and it is kept in the Windows Credential Manager — the per-user OS vault, protected by your logon session, visible and revocable in Control Panel ▸ Credential Manager, and the same vault a password manager fills. This tool stores no password of its own.

It is saved only after the server accepts it. Storing one that turns out to be wrong is worse than storing none: it comes back pre-filled and looking correct on every later attempt.

The entry is keyed on the server and the username, because the same person routinely has different passwords on a sandbox and on a customer’s server. Unticking the box, or Forget, removes it from the vault.

Working offline

The endpoint list and both documents work with no connection. Only sending a request needs one.

Finding an endpoint

The sidebar lists every catalogued endpoint by category. Search matches the name, the path, the category and the description.

The three pills filter by verb. They keep their own colour and simply fade when switched off:

GET reads   POST writes   DELETE destroys

The same colours appear on the tab and in the URL bar, because the verb is what decides whether a call is safe to fire at a live server.

Double-click an endpoint to open it. Each one opens in its own tab, so looking up a part id half way through composing a sales order no longer throws the order away.

Building a request

Everything is on one surface: the form on the left, what you are composing on the right, the response underneath. Both splitters drag.

The form

  • Path parameters — the {id} parts of the URL. An unfilled one stays visible in the URL preview rather than collapsing into something that looks valid and then 404s.
  • Query parameters — the documented ones are laid out for you; hover a field for what it means. Add your own with + Add. A parameter with no value is left out entirely.
  • Custom headers — rarely needed. Authorization: Bearer … and Content-Type are added for you.

Body and fields

The body editor and the documented field list sit side by side, because writing a body while reading which fields are required is the main thing anyone does here. Reset puts the documented template back; Fields ▾ hides the list when you want the width.

On a GET with a documented field list there is no body to write — those fields describe what comes back — so the pane becomes a response reference instead.

Enter sends, from any single-line field. Inside the body, SQL and import editors Enter is a new line and Ctrl+Enter sends — losing a half-typed body to a stray keystroke costs more than the shortcut saves.

Invalid JSON is caught before the request goes out, with the actual parse error. The server would only answer 400 with something less useful.

Importing data

/api/import/{name} is one endpoint covering 67 different record layouts, so it gets its own pane.

  • Import type — click anywhere in the box to open the list. These are the only names the server accepts, spelled exactly; each is labelled with the directions it supports.
  • Headers — picking a type calls /api/export/{name}/header and lays out a template row. The layouts are documented, but asking the server gives you this instance’s header row — with its custom fields, in its column order — so it is what this database will actually accept rather than what the general documentation describes. Use Fetch headers to ask again.
  • CSV or JSON — the toggle converts what is already typed rather than discarding it, and sets the right Content-Type.
  • Files — drop a .csv, .txt or .json anywhere on the pane. The format is decided by what is in the file, not by its extension.
The JSON form is a 2-D array, not an array of objects. The first inner array is the header row: [["Num","Description"],["A-1","Widget"]]. Sending objects is the usual first mistake. Paste them anyway and they are converted for you.

The Data tab

The query endpoint has its own tab, because by now it carries an editor, kept results and a comparison view and is nothing like the other endpoints. It is the same pane the endpoint opens in the sidebar — one implementation, not a copy — so everything in The SQL editor and Saving and comparing results applies here too, and the endpoint still works from the sidebar exactly as before.

The schema browser

Down the left, every table in the connected database with its columns. Read from the server, so it shows the custom fields this instance has.

The filter matches two ways, and the second is the useful one:

  • type part of a table name to find the table;
  • type a column name to find the tables that have it — those arrive already expanded, showing just the columns that matched. Working out which table holds qtyCommitted is most of what anyone opens this for.

Double-click a table or column to drop it into the editor at the caret. Columns arrive qualified — soitem.qtyOrdered — because that is what a join needs, and deleting the qualifier is the easier of the two edits.

Refresh re-reads the schema from the server. It is otherwise cached per server, since it changes about as often as an upgrade.

The SQL editor

/api/data-query carries its whole statement in a query parameter. As an ordinary parameter row that is a single line you cannot read a join in, so it gets a real editor.

Colouring

Keywords purple, string literals green, numbers blue, comments grey italic. It re-colours shortly after you stop typing, so it never fights the caret.

Completion

Type two letters and a list appears under the caret: keywords, then the tables in this database. Type a table or alias followed by a dot — soitem. — and it offers that table’s columns instead.

Tab accepts. ↑↓ move, Esc dismisses, Ctrl+Space asks without waiting for a second letter. Enter is always a new line — binding it would turn every line break that happens to follow a word into a completion nobody asked for.

Table and column names are read from the connected database, not from a schema file, so they include the custom fields this instance has. They are fetched once per server and cached.

Format SQL

Uppercases the reserved words, puts each clause on its own line, indents AND / OR under their condition, and tidies the spacing — COUNT(*) rather than COUNT (*), no space before a comma.

It never touches a literal or a comment. The formatter works on parsed tokens, not on the raw text, so WHERE note = 'select from where' comes back exactly as you wrote it. A find-and-replace formatter would change what that query matches.

Only SELECT is allowed by the server. Column and table names are Fishbowl's own — the schema reference in the repo lists them.

Reading the response

TabWhat it shows
PrettyIndented, coloured JSON.
RawExactly what came back, unaltered.
TableRows, for anything that has them.
HeadersThe response headers.

Opens on sets which tab a response lands on and is remembered across sessions. Auto shows the table for a query with rows and Pretty for everything else. A chosen tab is stepped past where it makes no sense — opening on an empty Table would hide the error the response actually contains.

Colouring by meaning

Recognised values are coloured by what they mean, in both the table and the JSON view:

Fulfilled Issued Pending Approval Voided Entered

Matching is exact, never by substring — a chip around part of a description would be a lie. Unrecognised values stay plain; empty cells and null read muted italic.

Sorting

Click a column header. Every cell arrives as a string, so sorting them as text would give 10, 15, 2, 20; instead numbers sort as numbers, ISO dates chronologically, text as text. Money and percentages count as numbers. Blanks gather at one end.

The decision is made per pair of values, not per column, so one N/A in a quantity column does not push the rest back to text sorting.

Saving

Save… offers CSV and JSON for anything tabular; pick the type in the dialog and the format follows. CSV quotes every field, so a part number like 00123 keeps its leading zeros instead of arriving in a spreadsheet as 123.

Saving and comparing results

A query run against a live database cannot be re-run to get the same answer. That is the whole reason for keeping one: was this number different an hour ago? is unanswerable unless the earlier answer was written down.

Keep results stores each successful query on this machine — the last 40, oldest dropped as new ones arrive. Saved shows them.

ActionWhat it does
Double-click Loads that result back into the response pane. The badge reads kept Tue 14:22, not a fresh 200 OK.
Restore queryPuts its SQL back in the editor.
RenameLabels a run, for telling two similar ones apart.
Compare Diffs the selected run against what the response pane is showing now.

What Compare shows

The differences go into the response pane itself, so they sort, copy and save like any other result. A ± column marks each row:

  • + — in the current result only
  • − — in the kept result only
  • ~ — in both, but changed. Only the fields that moved show old → new, so the row stays recognisable.

Rows are matched on a key column so an edited row reads as one change rather than a deletion plus an insertion. The key is chosen by evidence, not by name: the first column whose values are unique and complete on both sides. A column called id that repeats — any join will do that — is rejected, because using it would pair unrelated rows and report nonsense. Without a key it compares whole rows and says so.

Servers

The picker in the header switches between saved servers, each with its own address and integrated-app identity. The gear beside it adds, edits and removes them.

Switching servers disconnects you. A token belongs to a session on the server that issued it; carrying it across would fail on the next call with a 401 that looks like an expired login.

Mark the servers that hold real data. While one of those is selected the header turns red, a banner appears, and every POST, PUT, PATCH or DELETE asks you to confirm before it goes.

The confirmation is per request, not a session-wide “I understand”. The point is to interrupt the one call that was not meant to go there, and a box ticked an hour ago interrupts nothing.

A new profile has the production box suggested from its address — anything that is not localhost and does not look like a sandbox. It is only ever a suggestion: a hostname is not evidence, and a copy of production called fishbowl-prod-copy would be flagged wrongly forever. You decide.

Variables

Write {{name}} in any field — a path parameter, a query value, a header, a body, a SQL statement — and it is replaced when the request is sent. The Variables panel at the bottom of the sidebar holds them.

An unknown name is not replaced. Sending is refused instead, naming the ones with no value. Substituting an empty string would build a URL that looks perfectly valid and quietly asks for the wrong record.

Capturing from a response

This is the part that matters. Fishbowl's own contracts force multi-step work — create a manufacture order, read back its id, issue it; create a sales order, then add a memo to it — and the id in the middle exists only in the response you just received.

Capture… on the response bar lists the fields in that response, shows what each holds, and puts the one you pick into a variable. Tick Do this automatically from now on and it repeats every time that request succeeds, so a sequence keeps itself up to date.

Paths are written id, customer.name, results[1].num. A path that does not start at an array is also tried inside results, because every search endpoint wraps its rows in that envelope.

Saved requests

Save in the request bar keeps a filled-in request by name; the Saved panel opens them again. History is still there for the last 60 calls, but it dies with the session and is ordered by accident — this is for the handful you run every day.

They are stored with the {{placeholders}} intact rather than with whatever those resolve to right now, so one saved request works against every server instead of being welded to the one it was recorded on. Capture rules are saved with it.

cURL, and BI reports

Copy as ▾ in the request bar offers three things:

FormatFor
URLThe address as it will be sent.
cURL command Pasting into a ticket or a chat. The token is replaced with <TOKEN> — a live session token pasted into a ticket is a credential leak, so it is never included, even though that leaves the command one edit short of runnable.
runRestApiAsync call Pasting into a BI report. A report runs inside the Fishbowl client and uses the session the client already holds, so the snippet carries no token and no server address — which is exactly the part people get wrong translating a cURL command by hand.

Fill in from a cURL command works the other way: copy the command a colleague ran and the form fills itself in. Anything the command carries that this endpoint does not document still comes across as an extra row rather than being dropped.

Access rights

Where an endpoint's description names the right it needs, a chip under the description says so — green when the signed-in user has it, red when they do not.

A 403 from Fishbowl does not say which right was missing, so the usual next step is guessing whether the payload is wrong or the account is, and that guess costs far more than the call did.

Why most endpoints show no chip

Because most endpoints do not document a right. In the 26.9 API documentation, 7 of 107 endpoints name one, all of them GETs:

EndpointDocumentedAccess right
GET /api/manufacture-orders/{id}MO_VIEWManufacture Order-View
GET /api/purchase-orders/{id}PO_VIEWPurchase Order-View
GET /api/sales-orders/{id}SO_VIEWSales Order-View
GET /api/shipmentsSHIP_VIEWShipping-View
GET /api/shipments/{id}SHIP_VIEWShipping-View
GET /api/picksPICK_VIEWPicking-View
GET /api/picks/{id}PICK_VIEWPicking-View

Everything else — POST /api/purchase-orders/{id}/issue among them — is silent on the subject. Fishbowl certainly enforces a right there; it just does not publish which one. A blank chip means undocumented, never unrestricted.

Nothing is inferred from a path. If the documentation names a right this tool does not recognise, the chip says what was documented and makes no claim about whether you have it — a wrong prediction would send someone to an administrator to fix a permission that was never the problem. Guessing that /issue needs Purchase Order-Issue would be a good guess, and a good guess is still the wrong thing to put in front of someone debugging a 403.

Users the chip stays quiet for

Two accounts get no chips at all, because for them it could only ever be noise:

  • Anyone holding Full Rights. That entry means everything, by definition — they cannot be blocked.
  • The built-in admin. It belongs to no user group, so there are no useraccess rows to enumerate and the login returns an empty list. That is the absence of a rights record, not a user without rights; reading it the other way put a red cross on every endpoint for the one account that can certainly call them all.

Sign in as a restricted user and the chips come back.

Keeping the endpoint list current

Nothing about an endpoint is built into this program. The sidebar, the forms, the field tables and the body templates are all generated from a catalog, and the catalog can be brought up to date from the server's own /apidocs.json — so a newer server's endpoint is a new record, not a new release.

The tool checks quietly at start-up and says so in the status bar. Check for updates opens the review, which lists every proposed change with its own checkbox.

What an update will and will not do

  • Adds endpoints the server documents and the catalog does not.
  • Refreshes parameters, fields and body templates on endpoints that already exist.
  • Leaves the wording alone. The catalog's descriptions carry notes the published text does not — which call consumes an order number, which access right is really needed — so only shape is compared.
  • Removes nothing automatically. An endpoint the server does not mention is usually a curated addition, or an older server; those arrive unticked and need a second confirmation.

Reset to the shipped catalog throws every applied update away.

Kept results and variables are real data. Query output from a live database, and whatever you captured into a variable, sitting unencrypted in your profile. Clear all removes each of them; turning Keep results off stops new ones being written but leaves what is already there.
