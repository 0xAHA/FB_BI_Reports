1 Which API am I writing against?

A practical starting point for writing an integration against Fishbowl Advanced: what must exist before the first line of code, how to authenticate, and the handful of patterns that cover most integrations.

The endpoint reference is served by your own Fishbowl server while it is running — it always matches the version you are on, which no external document can:
  • http://<FB_SERVER_ADDRESS>:2456/apidocs — rendered, browsable view
  • http://<FB_SERVER_ADDRESS>:2456/apidocs.json — the same content as machine-readable JSON, no authentication needed
This guide covers what those docs assume you already know. See §6 for how to use them.
Companion tool. Fishbowl_Advanced_API_Tool.htm sits next to this guide. Log in and you can exercise every endpoint below interactively — exact request, response, and status code — before you commit anything to code. Start it via Launch_Advanced_API_Tool.bat; double-clicking the .htm gives you a CORS-blocked page (see §6).

Fishbowl exposes two APIs:

TransportHTTP + JSONJSON or XML over a raw TCP socket
Default port245628192
AuthPOST /api/login → bearer tokenSession ticket — and a REST token works as one (§6)
Callable from a browserYesNo — raw sockets are not available to browser JS

Write new integrations against REST. But be aware REST does not cover the full Fishbowl feature set — there are real gaps, and the legacy API fills a good number of them. Treat legacy as the fallback you reach for deliberately, per operation, not as an alternative to design against. §6 covers what it's good for and how to call it.

2 Before you write any code

Five things must exist, in this order. Skipping any of them produces a login failure that looks like bad credentials but isn't.

1

An application identity

Every client identifies itself with a name and a numeric ID that you choose:

{
  appName: "Acme Warehouse Sync",   // shown to the admin in Fishbowl
  appId:   4021                     // integer, yours to pick, keep it stable
}

Pick the ID once and never change it — Fishbowl keys the approval record off it. Changing either value registers a new application that needs approving all over again.

2

Administrator approval

The first POST /api/login from a new appId registers the application and is then rejected — Fishbowl returns 401 with a message mentioning approval. An administrator must then:

Open Setup → Settings → Integrated Apps tab, find the entry matching your appName, and tick the Approve checkbox on the right-hand side. Then log in again.

Build this into your onboarding instructions. It catches out every new integrator exactly once.

3

A dedicated integration user — with MFA off

Do not reuse a human's login, because:

  • Every logged-in session consumes a Fishbowl licence seat. A runaway integration that never logs out will exhaust the customer's seats.
  • Everything the app does is attributed to that user in the audit trail. You want that legible.
  • You can restrict it precisely to what the app needs, and revoke it without disturbing a person.
  • Humans are the ones who get MFA enrolled — and MFA breaks unattended logins outright.

Multi-factor authentication

Whether MFA belongs on the account depends entirely on who is typing the password. Decide which shape your app is before you go anywhere near this setting — the two cases pull in opposite directions:

App shape Who logs in MFA
Interactive
desktop tool, mobile app, portal — a person is at the keyboard		 Each individual user, with their own Fishbowl credentials. Everything is attributed to the real person. Fine — support it. Handle the challenge and let the user type their code.
Backend / unattended
scheduled sync, middleware, webhook receiver, ETL		 One dedicated service username created for this integration and nothing else. Must be off. Nothing can produce a code at 3 a.m.
A backend integration must have its own username with MFA disabled. The code lives in a human's authenticator app and rotates every 30 seconds, so there is nothing a scheduled job can read. Never point a backend service at a person's account — that account will get MFA sooner or later (see the bypass counter below), and the integration dies the day it does. Compensate with a strong generated password, minimal access rights, and network restrictions on who can reach port 2456.

Handling the challenge (interactive apps)

If the user has MFA enabled, POST /api/login answers the first attempt with 401 and the response header MFA: Required. You then resend the same payload with mfaCode set to the current 6-digit TOTP code from that user's authenticator app.

In UI terms: attempt the login normally, and only reveal a code field when that header comes back. Don't ask every user for a code up front — most accounts won't be enrolled. Clear the field after a successful login; the code is single-use and expires within 30 seconds, so a rejected retry usually means the code went stale rather than the user mistyping it.

deviceId makes this bearable for a tool someone opens daily. Send a stable unique string on a login where you do supply a valid mfaCode, and Fishbowl records it as a trusted device (with an expiry date) and stops challenging that machine. Generate it once and persist it — a fresh value each launch mints a new trusted-device row every time and defeats the point.

deviceId is not a way to make a backend service work under MFA. It still has to be seeded by a human supplying a real code, and it expires. Fine for a desktop tool; fragile for a server, and it will fail silently on whatever night the trust lapses.

Keep the service account out of the desktop client

MFA is not purely per-user — two system properties govern it site-wide:

PropertyMeaning
MfaRequiredWhen true, the site pushes every user toward MFA enrolment.
MfaBypassLimitHow many times a user may defer enrolling before it is forced (10 by default).

The enrolment prompt — and therefore the counter — belongs to the desktop client login. Each time a user is offered enrolment and defers, sysuser.mfaBypassCounter increments; once it passes MfaBypassLimit they can no longer defer.

A service account that only ever authenticates through the REST API is never prompted, so its counter never moves and MFA is never forced on it — even on a site with MfaRequired = true. The rule that follows is simple: never sign into the Fishbowl desktop client as your integration user.

That is the whole risk, and it is entirely avoidable. Somebody "just checking the integration account works" by logging into the client is what starts the clock; do it enough times and the account is forced into enrolment, and the next scheduled run fails with a challenge nothing can answer. Nothing in your code changed, which makes it a miserable thing to diagnose after the fact. If you need to verify the account's permissions, do it from the API or from an admin session looking at that user's config — not by logging in as them.

Before go-live, confirm the account is clean. This query gives you the whole picture in one shot — a service account should show not enrolled with a counter of 0: 

SELECT u.userName,
       CASE WHEN LENGTH(u.mfaSecret) > 0 THEN 'ENROLLED' ELSE 'not enrolled' END AS mfaState,
       u.mfaBypassCounter AS deferralsUsed,
       (SELECT sysValue FROM sysproperties WHERE sysKey = 'MfaBypassLimit')  AS bypassLimit,
       (SELECT sysValue FROM sysproperties WHERE sysKey = 'MfaRequired')     AS mfaRequired
FROM sysuser u
WHERE u.activeFlag = 1
ORDER BY (LENGTH(u.mfaSecret) > 0) DESC, u.mfaBypassCounter DESC

A non-empty mfaSecret means that account is enrolled and will be challenged on every API login — a backend integration on that account is already broken, or about to be. A non-zero mfaBypassCounter on a service account is the warning sign: it means somebody has been logging into the desktop client as that user, and it will eventually be forced to enrol.

The MFA: Required handshake and deviceId behaviour above are documented in the server's own apidocs.json. The bypass-counter columns and the two system properties are read from the schema; the exact enrolment trigger is not formally documented, so treat the specific numbers as indicative and verify against the customer's site.
4

The right access rights on that user

The API enforces the same access rights as the client UI. Grant the module rights matching what the app will actually do, and nothing more:

If the app…The user needs (at minimum)
Reads parts / inventory levelsPart-View, Inventory-View
Reads or writes sales ordersSales Order-View + create/edit rights
Reads or writes purchase ordersPurchase Order-View + create/edit rights
Creates or issues manufacture ordersManufacture Order-View + create/edit rights
Adds, cycles, or scraps inventoryInventory-View + the relevant adjustment rights
Reads part costsInventory-Show Part Cost
Overrides SO prices or discountsSO_PRICE_OVERRIDE (+ the specific override right)
Ships or receivesShipping-* / Receiving-*
Runs /api/data-queryrights covering every table the SQL touches
If a call returns data you did not expect to be missing — empty lists, absent cost fields, a bare 403 — suspect access rights before you suspect the endpoint.
5

Location group access

The user's assigned location groups scope almost everything: inventory quantities, order visibility, and which warehouse a new order defaults to. Assign the integration user to the location groups it should see, and mark a sensible default.

An app that "can't find" stock that is plainly there is nearly always looking from the wrong location group.

3 Getting started — a minimal client

Runs as-is in a browser or in Node 18+ (both have fetch built in).

3.1 Log in

const BASE = 'http://fishbowl-server:2456';   // your server address, port 2456

async function login(username, password, mfaCode) {
  const res = await fetch(BASE + '/api/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      appName:        'Acme Warehouse Sync',
      appDescription: 'Nightly stock and order sync',
      appId:          4021,
      username,
      password,
      ...(mfaCode ? { mfaCode } : {})
    })
  });

  const body = await res.json().catch(() => ({}));

  // Approval is checked BEFORE credentials, so this fires even if the password
  // is also wrong. Fix approval first, then worry about the rest.
  if (res.status === 401 && /approval/i.test(body.message || '')) {
    throw new Error(
      'App registered but not approved. An administrator must tick Approve against ' +
      'this app in Setup -> Settings -> Integrated Apps, then try again.'
    );
  }

  // MFA challenge. Signalled by a RESPONSE HEADER, not the body.
  // Interactive app: prompt for the code and call login() again with it.
  // Backend service: this should never fire — see 2.3, the service account
  // must not be MFA-enrolled and must never be used in the desktop client.
  if (res.status === 401 && res.headers.get('MFA') === 'Required') {
    const err = new Error('MFA code required for ' + username);
    err.code = 'MFA_REQUIRED';
    throw err;
  }

  if (!res.ok) throw new Error(body.message || ('Login failed: HTTP ' + res.status));

  return body.token;   // keep this in memory for the life of the session
}
Whether you implement the MFA branch depends on your app's shape — see 2.3. An interactive app should prompt for the code; a backend service should treat this as a misconfiguration, because a TOTP code cannot be produced by an unattended process.

3.2 A wrapper for every other call

let token = null;

async function api(path, { method = 'GET', query, body, headers = {} } = {}) {
  const url = new URL(BASE + path);
  for (const [k, v] of Object.entries(query || {})) {
    if (v !== undefined && v !== null) url.searchParams.set(k, v);
  }

  const res = await fetch(url, {
    method,
    headers: {
      'Authorization': 'Bearer ' + token,
      ...(body ? { 'Content-Type': 'application/json' } : {}),
      ...headers
    },
    body: body ? JSON.stringify(body) : undefined
  });

  const text = await res.text();
  const data = text ? (() => { try { return JSON.parse(text); } catch { return text; } })() : null;

  if (res.status === 401) throw new Error('Session expired or not authenticated - log in again.');
  if (!res.ok) throw new Error((data && data.message) || ('HTTP ' + res.status + ': ' + text));
  return data;
}

3.3 Read something

// Search parts. pageNumber / pageSize work on every search endpoint (default 100).
const parts = await api('/api/parts', {
  query: { number: 'B2', active: true, pageNumber: 1, pageSize: 50 }
});

// Fetch one by id
const part = await api('/api/parts/' + parts[0].id);

// Inventory levels, scoped to a location group
const inv = await api('/api/parts/inventory', {
  query: { locationGroupId: 1, includeZeroQuantities: false }
});

3.4 Write something

Writes are POST with a JSON body. Reference objects are always { "id": n }:

const mo = await api('/api/manufacture-orders', {
  method: 'POST',
  body: {
    number: '',                          // blank = let Fishbowl assign
    locationGroup: { id: 1 },
    dateScheduled: '2026-08-01',
    configurations: [
      { bom: { id: 12 }, quantity: 25 }
    ]
  }
});

await api('/api/manufacture-orders/' + mo.id + '/issue', { method: 'POST' });

3.5 Always log out

async function logout() {
  await fetch(BASE + '/api/logout', {
    method: 'POST',
    headers: { 'Authorization': 'Bearer ' + token, 'Content-Type': 'application/json' }
  });
  token = null;
}
This matters. Logout releases the licence seat. A long-running service should log in once, hold the token, and log out on shutdown — not log in per request, and never log in per request without logging out. Wire it into your process's shutdown handler.

4 Beyond the typed endpoints

4.1 Read anything with Data Query

GET /api/data-query?query=<SQL> runs a read-only SELECT against the Fishbowl database and returns JSON rows. Use it for reporting shapes and for the things that have no typed endpoint — the image table, audit tables, custom-field values, aggregate rollups: 

const sql = `
  SELECT p.num, p.description, i.type, i.imageThumbnail AS img
  FROM part p
  INNER JOIN image i ON i.recordId = p.id AND i.tableName = 'part'
  WHERE p.num = 'B201'
`;
const rows = await api('/api/data-query', { query: { query: sql } });

// Image blobs come back as raw base64:
//   imgEl.src = 'data:' + rows[0].type + ';base64,' + rows[0].img;

Two caveats:

  • SELECT only. There is a write-enabled variant (/api/unsafe/deprecated/data-query) but it requires the FbPartnerAPI partner licence and will run INSERT/UPDATE straight against the database with no undo. Treat it as a last resort, not a shortcut around the typed endpoints.
  • You own the query plan. Nothing stops you writing a query that table-scans the whole inventory. Filter on indexed columns, and prefer batching with IN (…) over one query per row.

4.2 Bulk load with CSV import

POST /api/import/{name} accepts the same CSV formats as the client's import screens, so an existing import file works unchanged: 

await fetch(BASE + '/api/import/Customers', {
  method: 'POST',
  headers: { 'Authorization': 'Bearer ' + token, 'Content-Type': 'text/csv' },
  body: csvText
});

GET /api/export/{name}/header returns the exact column headers for an import type — call it once and build your CSV to match rather than guessing column order.

Import is the right tool for anything the REST layer can't write directly (part updates being the common case) and for any volume load — it is far faster than a loop of single writes.

5 Things that will bite you

Sessions expire

Treat any 401 on a previously working call as "log in again and retry once", not as a fatal error. Don't retry in a tight loop.

One session per app instance

Concurrent logins from the same user each take a seat. Share one token across your worker threads rather than logging in per worker.

CORS, if your app runs in a browser

The Fishbowl server does not send permissive CORS headers, so a page served from file:// or another origin will have its requests blocked by the browser before they ever reach Fishbowl. Options, in order of preference: serve your app from the same origin, put a small proxy in front, or — for local testing only — launch a browser with web security disabled (Launch_Advanced_API_Tool.bat next to the API tool does exactly this).

Dates

Send ISO YYYY-MM-DD (or YYYY-MM-DDTHH:mm:ss). Don't send the user's localised short-date format.

Next-number endpoints consume the number

/next-number on sales, purchase, manufacture, and transfer orders advances and reserves the counter whether or not you go on to create the order. Don't call it speculatively.

Money and quantities

They come back as numbers, but round with the server's rules before displaying totals — don't accumulate floats and hope.

Test against a copy first. Restore the customer's database into a test instance and point your BASE at that. Order creation and inventory adjustments are not undoable.

6 The legacy API — filling REST's gaps

REST does not cover everything the Fishbowl client can do. Where it stops, the older socket API usually keeps going — at the cost of a much less pleasant transport.

When you actually need it

Work through REST first: it is versioned, self-documenting, and reachable from anything that speaks HTTP. Reach for the legacy API only when you have confirmed the operation you need has no REST endpoint. Broadly, the legacy API still has ground REST has not covered:

  • Receiving — REST has no receiving at all; the legacy API can fetch and save receipts.
  • Shipping beyond the basics — saving and voiding shipments, and a one-call automatic pick-pack-ship.
  • Picks — REST can search and read them; the legacy API can save them.
  • Work orders — read-modify-write on the whole WO record. REST has only WO memos.
  • Setup writes — UPCs, tax rates, discounts, part images, default part locations.
  • Reports — print and email a Fishbowl report from code.
  • Accounting reads — account lists and balances; taking a payment.

That is a characterisation, not an inventory. There are around 65 request types and this page deliberately does not list them — get the reference from Fishbowl support (see §7) and check it against the REST docs for the version you are on, because the boundary moves with every release.

Some requests answer 900 — Success! This API request is deprecated and could be removed in the future. Treat a 900 as a working call on notice: it succeeded, but plan its replacement. And the reference itself is not complete — there are working requests absent from it, so if support's docs don't list what you need, ask before concluding it doesn't exist.

Reaching it — why there's no browser option

The legacy API is not HTTP. It is a raw TCP socket, by default on port 28192, with its own framing: a 4-byte big-endian length followed by that many bytes of payload — in both directions. 

[ int32 length ][ payload bytes ]      // request, and response, and every message
Browser JavaScript cannot open a raw TCP socket — there is no API for it, and fetch/WebSocket cannot speak this framing. So a browser-based app cannot call the legacy API directly, at all. That is why Fishbowl ships the samples in C# and Java. Any language with a socket library works — C#, Java, Python, Go, Node — but it has to be server-side code.

So there are exactly two ways in:

RouteHowAvailable to
Direct socket Open TCP to host:28192, write length-prefixed frames yourself. Server-side code in any language. Not a browser.
runApiRequest() A BI-report bridge: the Fishbowl client already holds the socket and the session, and proxies your request over it. JavaScript, but only inside a Fishbowl BI report.
If your target is a BI report, the socket problem disappears — use runApiRequest() and skip the rest of this section's plumbing. If your target is a standalone integration, you are writing a socket client.

Authentication — borrow a REST token

The legacy API has its own LoginRq, which returns a ticket key you then put in every subsequent request. It also sends the password as plain text over the socket, which is why Fishbowl discourages it.

The token from a REST /api/login works as the legacy Ticket Key. So authenticate over REST — encrypted, MFA-aware, one approval record — and reuse that token on the socket. You get the legacy surface without ever putting a password on the wire in clear text, and you keep a single login path. Do this rather than LoginRq.

Examples

The envelope

Every request is wrapped in FbiJson (or FbiXml — both transports exist and take the same shape). The ticket rides in the envelope; the actual request goes in FbiMsgsRq: 

{
  "FbiJson": {
    "Ticket":    { "Key": "<REST token, or the key from LoginRq>" },
    "FbiMsgsRq": { "ExecuteQueryRq": { "Query": "SELECT num FROM part LIMIT 10" } }
  }
}

The response mirrors it. FbiMsgsRs carries an overall statusCode, and each nested <Name>Rs carries its own — so check both: 1000 is success. 

{
  "FbiJson": {
    "Ticket":    { "Key": "…" },
    "FbiMsgsRs": {
      "statusCode": 1000,
      "ExecuteQueryRs": { "statusCode": 1000, "Rows": { "Row": [ "…csv…" ] } }
    }
  }
}

A minimal Node socket client

This is the whole transport — framing, buffering, and the envelope. Everything else is choosing a request name and body. 

const net = require('net');

class FishbowlLegacy {
  constructor(host, port = 28192) { this.host = host; this.port = port; this.key = ''; this.buf = Buffer.alloc(0); }

  connect() {
    return new Promise((resolve, reject) => {
      this.sock = net.createConnection({ host: this.host, port: this.port }, resolve);
      this.sock.once('error', reject);
    });
  }

  // body: { SomeRq: { … } } — the FbiJson envelope is added here.
  send(body) {
    const payload = Buffer.from(JSON.stringify({
      FbiJson: { Ticket: { Key: this.key }, FbiMsgsRq: body }
    }), 'utf8');

    const frame = Buffer.alloc(4 + payload.length);
    frame.writeInt32BE(payload.length, 0);   // 4-byte BIG-endian length
    payload.copy(frame, 4);

    return new Promise((resolve, reject) => {
      const onData = (chunk) => {
        this.buf = Buffer.concat([this.buf, chunk]);
        // A response can arrive in several chunks — wait for the full frame.
        if (this.buf.length < 4) return;
        const len = this.buf.readInt32BE(0);
        if (this.buf.length < 4 + len) return;

        const msg = this.buf.slice(4, 4 + len).toString('utf8');
        this.buf = this.buf.slice(4 + len);
        this.sock.removeListener('data', onData);
        try { resolve(JSON.parse(msg)); } catch (_) { resolve(msg); }
      };
      this.sock.on('data', onData);
      this.sock.once('error', reject);
      this.sock.write(frame);
    });
  }

  close() { if (this.sock) this.sock.end(); }
}

Used with a REST token, so no password touches the socket:

const fb = new FishbowlLegacy('fishbowl-server');
await fb.connect();
fb.key = await login('svc_integration', process.env.FB_PASSWORD);   // §3.1 — REST login

const rs = await fb.send({ ExecuteQueryRq: { Query: "SELECT num, description FROM part LIMIT 5" } });

const inner = rs.FbiJson.FbiMsgsRs;
if (Number(inner.statusCode) !== 1000) throw new Error('Legacy call failed: ' + inner.statusCode);
console.log(inner.ExecuteQueryRs.Rows.Row);      // CSV lines

fb.close();

The same thing from a BI report

runApiRequest(requestName, jsonBody) is synchronous and returns a JSON string. Note it takes and returns the un-enveloped form — no FbiJson, no Ticket, because the client supplies the session: 

// Read-modify-write is the standard shape for the legacy Save*Rq calls:
// GET the whole record, change one field, send the WHOLE record back.
// Sending a partial record resets the fields you left out.
const got = JSON.parse(runApiRequest('GetWorkOrderRq',
  JSON.stringify({ GetWorkOrderRq: { WorkOrderNumber: woNum } })));

if (got.GetWorkOrderRs && Number(got.GetWorkOrderRs.statusCode) === 1000) {
  const wo = got.GetWorkOrderRs.WO;
  wo.CalCategoryID = newCategoryId;                       // the one change

  const saved = JSON.parse(runApiRequest('SaveWorkOrderRq',
    JSON.stringify({ SaveWorkOrderRq: { WO: wo } })));

  if (Number(saved.SaveWorkOrderRs.statusCode) !== 1000) {
    throw new Error(saved.SaveWorkOrderRs.statusMessage);
  }
}
runApiRequest is synchronous — it blocks the report's UI thread for the round trip. Fine for a button click; do not put it in a loop over hundreds of rows without showing progress. Where a CSV import can do the same job in one call, prefer that.

Running a CSV import

ImportRq exposes every CSV import the client has, named without spaces (ImportSalesOrder, ImportScrapData, ImportVendors, …). It is the officially recommended way to create orders, and the fastest route for any bulk write: 

// ImportHeaderRq returns the exact column order for an import — call it once
// and build your rows to match rather than guessing.
const hdr = JSON.parse(runApiRequest('ImportHeaderRq',
  JSON.stringify({ ImportHeaderRq: { Type: 'ImportScrapData' } })));

const rows = [ /* header line, then one line per record, CSV-quoted */ ];
const res = JSON.parse(runApiRequest('ImportRq',
  JSON.stringify({ ImportRq: { Type: 'ImportScrapData', Rows: { Row: rows } } })));

if (Number(res.ImportRs.statusCode) !== 1000) throw new Error(res.ImportRs.statusMessage);

Editing orders is the notable limitation. Header-level fields (addresses, terms) can be updated with the matching …Details import, but to change line items the documented approach is to void the order and re-create it. Fishbowl's own advice is to suffix the new order number (-1, -2) so the original stays searchable.

7 Where to go next

Full REST reference — machine readable

Your own server publishes its complete API documentation as JSON, no authentication required:

http://<FB_SERVER_ADDRESS>:2456/apidocs.json

This is the authoritative reference: it matches the exact version you are running, which no external document can. Structure: 

{
  "version": "26.6",
  "sections": [
    {
      "name": "Transfer Orders",
      "description": "...",
      "helpLink": "https://help.fishbowlinventory.com/advanced/...",
      "objectExample": { /* a full example object */ },
      "objectAttributes": [ /* every field, typed and described */ ],
      "endpoints": [
        {
          "id": "create-transfer-order",
          "title": "Create a transfer order",
          "description": "...including the access rights it enforces",
          "endpoint": { "verb": "POST", "path": "/transfer-orders" },
          "attributes":     [ /* request fields, nested via children[] */ ],
          "requestObject":  { "curl": "curl --location ..." },
          "responseObject": { "json": { /* a real example response */ } }
        }
      ]
    }
  ]
}

Note endpoint.path omits the /api prefix — prepend it. Path parameters appear as either :id or {id} depending on when the endpoint was written; treat both as placeholders.

One thing it does not document: query parameters for the GET search endpoints. pageNumber and pageSize work everywhere (page size defaults to 100); the rest appear only in the HTML docs page and in the API tool's registry.

This is the format to hand an AI coding assistant. Fetch it, save it, and paste the relevant section into your prompt — it contains the field list, types, and a real response example, which is everything the assistant needs to generate a correct payload.

The same content as a browsable page. It is a JavaScript single-page app, so fetching the URL with a script or an AI tool returns an empty shell — use apidocs.json for that. Older builds may not serve this path at all; apidocs.json is the reliable one.

Legacy API reference

Not published online. Request the documentation from Fishbowl support, quoting your Fishbowl version. You should get three HTML references — one per transport (API JSON, API XML) plus a developer-hook page — and ask for the C# and Java sample projects too: they are the only place the socket framing is actually demonstrated, and they save you reverse-engineering it. See §6 before you start.

Two caveats on those docs. The JSON reference covers only a handful of requests — the XML one is the fuller catalogue, and both transports accept the same request shapes, so read the XML reference even if you intend to send JSON. And the catalogue is not exhaustive: working requests exist that it does not list, so ask support rather than assuming something is unavailable.

Interactive testing

Fishbowl_Advanced_API_Tool.htm, in the same folder as this guide — endpoint browser, login flow, request builder, CSV import zone, and a debug console that shows the raw request and response for every call. The fastest way to confirm a payload shape before you commit it to code.

Launch it with Launch_Advanced_API_Tool.bat, not by double-clicking the .htm. Opened normally, the page runs from a file:// origin and the browser blocks every request to Fishbowl before it leaves the machine — you get opaque network failures rather than API errors. The .bat starts a browser with web security disabled so the cross-origin calls go through. That is a deliberate local-testing compromise; don't use that browser profile for anything else.
