# Paperwork proof of concept

Replacing the Jasper (iReport) paperwork with BI reports that print and save as
PDF like the standard Fishbowl forms. Each document is a replica of a stock
report under `server/reports/`, named after its jrxml file:

| Page (source → `dist/`) | Stock report | Record name | Apps in (fb-launch) |
|---|---|---|---|
| `SOReport.htm` | SalesOrder/SOReport.jrxml | `Sales Order Report` | SO |
| `SOInvoiceReport.htm` (built from SOReport.htm, Invoice on) | SalesOrder/SOInvoiceReport.jrxml | `Sales Invoice` | SO |
| `POReport.htm` | PurchaseOrder/POReport.jrxml | `Purchase Order Report` | PO |
| ~~`PickTicket.htm`~~ archived 2026-10-14 | Picking/PickTicket.jrxml | `Pick Ticket` now holds `iReport_Ports/Picking/PickTicket.htm` | PICK |
| `PackingList.htm` | Ship/PackingList.jrxml (SO / PO / TO V2 layouts) | `Packing Slip` | SHIP |
| `ShippingInvoice.htm` | Ship/ShippingInvoice.jrxml (invoice / pro-forma; AU / US / CA) | `Shipping Invoice` | SHIP |
| `WOTraveler.htm` | WorkOrder/WOTraveler.jrxml | `Work Order Traveler` | WO |

Each page's header comment lists its settings, options and its deliberate
deviations from the jrxml; `specs/` holds the jrxml specs they were built from
(Pick Ticket was built from the jrxml directly). The sections below describe the
Sales Order report in detail; the others work the same way.

**Status:** proof of concept. It has been tested on the desk against demodb
only. It has not been tried in the Fishbowl client yet; Phase 0 below covers
that.

## How it prints

The BI Report module already has its own **Print**, **Save → PDF** and
**Email** toolbar buttons. The report page itself is the paper, so `fb-doc.js`
lays the order out as fixed-size sheets:

- **On every sheet:** the page header (logo, company, title, Order # and Date,
  barcode) and the page footer ("Page X of Y").
- **On the last sheet only:** the last-page footer (SO Notice, totals, Pay
  Online), pinned to the bottom. If it does not fit, the final rows move to a
  new sheet with it, so the totals never sit alone.
- **Line-item tables:** the column header repeats on every sheet.
- **Kits:** a kit parent stays with its first child. When a kit runs over a
  page break, its header is repeated as "(continued)".
- **BOM rows:** they stay attached to their work-order line.
- **Long text:** order notes and line notes split across sheets by line.
- **Zebra striping:** restarts on each sheet, as Jasper's does.
- **Paper size:** comes from the report's **Page_setup** setting, A4 by
  default. The table always spans the content width.
- **Column widths:** each column type has one standard width. Hiding a column
  gives its space to the text columns. When too many columns are shown, the
  table steps down one font size; it never runs off the page.

## Fishbowl report settings

The BI Report module supports **report settings** (the Parameters button). A
setting is written in the page as a token: a dollar sign, a code, then
`{Title|default|Group}`. Fishbowl substitutes the chosen value before the page
loads; the editor preview substitutes the default.

The codes are listed in `QueryParamTypeConst` in `fbconstants.jar`. They
include `SO` (Fishbowl's own SO picker, which returns the order id), `PRINT`
(page size and margins), `CHECK`, `TEXT`, `NUM`, `DATE`, `CUST`, `PART`, `PO`,
`WO` and `PICK`.

How they behave:

- Values are stored on the BI Report record, so they are shared by every user.
- Only users with Edit Settings rights on the report can change them.
- Substitution is plain text replacement across the whole page, like the
  Script and Style directives. Write each token once, inside a
  `<script type="text/plain">` block, and never in comments or in shared code.

This report uses three settings:

- **Sales_Order:** adopted once when it changes; after that, each user's
  in-page pick stands.
- **Invoice**
- **Page_setup**

The same script serves two BI Reports in Fishbowl: "Sales Order", and "Sales
Invoice" with Invoice ticked.

## Queries

`FBDoc.q(sql, params)` fills `?` placeholders **inline** (escaped literals) and runs
plain `runQuery(sql)`. The client's bind-parameter form `runQuery({query, parameters})`
goes through a different server path that is refused unless the company "Data Access
API" setting is on and the user has the Data-View right; the refusal arrives as a bare
string. The harness emulates that refusal (`HARNESS_BIND=1` to allow it). Query
failures surface as "Error — <message>" in the status line and in the debug console.

Never select a bare `NULL` column: the server reads results through the MariaDB
driver, which types it as `byte[]`; Fishbowl's `Class.forName` then fails and the
whole query returns "An unknown error has occurred." The harness rejects such
columns the same way.

## Choosing the order

Opened from the Sales Order module's **Reports → Apps** (the
[report_btn](../report_btn/README.md) plugin), the report prints the open order straight
away: the plugin hands it over as `window.FB_LAUNCH`, read with `FBDoc.launch`. That
order is then **fixed**: the picker, ‹ › and Refresh are hidden, leaving **Print** and
**Settings** (the plugin window's own toolbar has Print / Save → PDF / Email). Paper size
and the Invoice switch are in the Settings drawer. The format and the module codes are in
[LAUNCH_CONTEXT.md](LAUNCH_CONTEXT.md). Opened any other way, the order comes from the
setting or the user's last pick. The harness emulates a launch with `?launch=<json>`.

Click the order box or ▾ to browse recent orders. Status chips (from `sostatus`) and a
Created period filter the list, typing searches SO number, customer and customer PO, and
each row shows status, date and total. Filters are remembered per user, and ‹ › step
through orders within them.

## Paper

The toolbar's Paper list shows what the **Page_setup** report setting resolved to
("Paper: A4 (report setting)"); picking another size is remembered per user. Only the
setting's paper size and orientation are used: the document keeps its own (Jasper)
margins, because the setting dialog's default 1 in margins squeeze the layout.

## Print geometry

The BI Report module's Save → PDF / Print ignores `@page { margin: 0 }`, applies
Chromium's default 0.4 in (10.16 mm) margins and shrinks anything wider than the
printable area to fit (measured: a full-bleed A4 sheet printed at 90.3%). So each
sheet is sized to the printable area (paper − 2 × 0.4 in), `@page` declares that
margin, and the document's own margins are sheet padding beyond it. On screen the
sheet sits in a full-size paper frame. The render tests lay the page out at the
printable width in print media and fail if anything is wider.

**Save → PDF / Email** use the page's own paper size and print at 100%. **Print**
goes through the Windows print dialog, which uses the *printer's* paper and
settings: if that paper differs from the document's (e.g. Microsoft Print to PDF
defaulting to Letter for an A4 document) Chromium shrinks each sheet to fit. Pick
the document's paper size in the dialog (Preferences → paper), or set Page_setup to
the paper the printers use. The probe prints "Printer page area" on the sheet,
which is what that print path laid out (CSS media queries in print see the print
settings' page, not the page's `@page` size).

## Options

The starting point is the stock report's saved options: the `reportparameter`
rows of `SOReport.jasper` and `SOInvoiceReport.jasper`. A customer's existing
Show / Column / FieldTitle / CustomField setup therefore carries over. Without
them, the report falls back to the jrxml defaults.

Admins can override options in Settings and **Save for everyone**. This uses
the FBLib.Settings master, stored in userProperties.

Number and date formats come from `sysproperties`: `REPORT_DECIMAL_PRICE`,
`_TOTAL`, `_QTY` and `REPORT_DATE_FORMAT`. The edition comes from `QBVersion`
(US, AU or CA/international), the footer message from `SO Notice`, and the
Order # prefix from `Barcodes have DI`.

## Phase 0: check the print path in the client (do this next)

1. Run `node build.js`.
2. Save `dist/Print_Probe.htm` as a BI script, then create a BI Report for it in
   a test database.
3. Open it and click Parameters. Set the three settings. Note what the dialog
   offers for Page_setup.
4. Copy the probe panel text. It shows the raw substituted values of the
   settings, whether bind parameters are refused on this database, and that
   inline binding works.
5. Use the toolbar's **Save → PDF**, **Print** and **Email**. For each, check:
   - the paper size;
   - that the PDF page count equals the sheet count shown on screen;
   - that the 100 mm ruler measures 100 mm;
   - that the grey stripes print;
   - that there is no blank last page and no browser header or footer;
   - that the link is clickable.

   Try the in-page Print button too.
6. Compare each document with the stock report's PDF for the same records. The
   documents need the deployed `fb-lib` and `fb-styles`.

## Deploying to the local Fishbowl

As of 2026-10-12, all seven documents deploy to the local Fishbowl server. Their
target is `fishbowl` (`tools/deploy/targets.js`), and the records use the names
in the table at the top.
- **What deploys.** Each deploy builds the page and sends `dist/<Doc>.htm`, never
  the source (`tools/deploy/built.js`).
- **Which edits redeploy:**
  - an edit to a page redeploys that page;
  - an edit to `SOReport.htm` also redeploys `SOInvoiceReport`;
  - an edit to `fb-doc.js` or `fb-doc-fonts.css` redeploys every document.
- **Access.** The records have no access rows, so only admins see them. Grant
  access with `node tools/deploy/fbdeploy.js --access "<groups>" <file>`.

## Sales Order: deliberate deviations from the jrxml

- **Joins:** LEFT joins throughout. In the jrxml, a null ship terms blanks the
  info strip.
- **Missing values:** no literal "null" for a missing phone, email, fax or
  salesperson.
- **Currency:** one source, `so.currencyId`, with the customer's currency as
  fallback. The jrxml mixes the two.
- **Widths:** info strips refit to the page instead of running off it past six
  columns. Item columns use the shared catalogue widths.
- **Ordering and continuation:** payments are ordered by date. Kit headers are
  repeated as "(continued)" across page breaks.

## Known gaps (Sales Order; each other page lists its own in its header comment)

- **Not tried in the client yet:** the print path, the setting formats and the
  bind-parameter support are what Phase 0 checks.
- **Header band:** fixed at 134 pt, as in the jrxml. A very long company address
  is clipped rather than growing the band.
- **Company address:** in the harness, `getCompanyAddress` is approximated with
  SQL. In the client, the real bridge runs the same server method as the jrxml.
- **Rounding:** money uses `Intl` half-up / half-even on the shortest decimal
  form. Java rounds the exact binary value, so a rare x.xx5 can differ by a
  cent.
- **Batch printing:** `FBDoc.paginate` takes several documents and numbers the
  pages of each separately, but the report UI prints one order at a time.
