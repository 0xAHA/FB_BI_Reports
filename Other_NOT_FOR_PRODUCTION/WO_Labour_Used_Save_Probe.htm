WO Labour Used + Scrap — SaveWorkOrderRq probe

Tests whether a labour line's QtyUsed can be adjusted via a standalone SaveWorkOrderRq (target left untouched), then reads the DB row back to confirm what actually persisted. Also tests the QtyScrapped field on the WO save (bottom section) as a possible replacement for the separate ImportScrapData CSV scrap flow — checking whether it actually moves on-hand stock or is cosmetic. Read-only until you click a Save/Fulfil button, which writes to the WO — demo DB only.
WO #:
To isolate the mechanism: on a fresh Entered WO, click Save labour QtyUsed and note whether the DB read-back persists (0→N or 0→0). Then click Start WO and Save again — if it only persists once Started, the report must pre-store labour AFTER the WO is started.
Decisive test: sets StatusID=40 and FG QtyUsed=target (a finish), but leaves the labour lines' QtyUsed exactly as already stored. If the stored values survive, the fix is "set labour while open, then fulfil". Only run on a disposable OPEN test WO (e.g. 220:001).
Tests whether setting a component line's QtyScrapped in the SaveWorkOrderRq actually scraps stock — the alternative to the separate ImportScrapData CSV flow used in Production_Scheduling. The on-hand delta (tag qty, typeid 30/40) is the decisive check: [STOCK MOVED] means a plain WO save can replace the CSV path; [no change] means QtyScrapped is cosmetic and the ImportScrapData flow is still required. Enter a New QtyScrapped on an inventory raw-material line (scrapping labour/non-inventory has no stock to move). Run the finish variant on a disposable OPEN WO.
RESULT (2026-07-25, DB-verified): COSMETIC. Setting woitem.QtyScrapped via SaveWorkOrderRq (at Entered and at status→40) wrote the DB field but created zero inventorylog transactions and moved no on-hand stock (LID-501 stayed 92, committed 0). It does NOT replace the ImportScrapData flow — actual scrap needs a real inventory transaction. Caveat: the finish variant went status→40 without committing a pick, so it didn't test scrap during a real finish; but the field fired nothing either way, and ImportScrapData scraps from general stock (no pick needed) so it's strictly more capable.
MO #:
Tests the REST Update a manufacture order endpoint (each config item has quantity + quantityFulfilled). Per the docs, configurations only update when the MO status is "Entered", and SO-linked MOs are skipped — so this can't set a finished WO's labour. After POST it re-GETs the MO and re-reads the WO's labour woitem.qtyUsed to show whether an MO-item change flows to the WO. Demo DB only.
